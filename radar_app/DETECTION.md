### Why the range ordering needs validation

The recording also contains isolated returns around **6.25 m**, and duplicated
club/multipath returns around **3 m**. Picking the furthest point alone would be
wrong. A candidate must form a coherent path in time, direction, range and Doppler,
and have a launch connection to an independently observed swing.

Not every true ball is visible beyond the club's *eventual* full reach. In the short
visible flights of captures 2 and 5, the strong evidence is that it is farther ahead
**at the same time** as the club and separates while the club slows. Capture 6 is
the complementary case: the ball appears clearly only **after** the near club path
has slowed/ended. It must not require three simultaneous club/ball observations.

The low-hop tail also advances just one range bin. Its stable measured Doppler is
consistent with a quantized range staircase, even though a three-sigma test of the
two endpoint coordinates alone rejected it. V2 intersects the reported range-cell
intervals after integrating Doppler, rather than treating cell centres as exact
positions or demanding an arbitrary minimum travel distance.

### Club-only validation

The same original point clouds are tested with the independently identified ball
returns withheld, retaining the club and far/noisy returns. All seven of these
counterfactual replays are unconfirmed. Ball-only versions also remain unconfirmed
because there is no independent swing evidence.

This exposed another bug during development: joining a club-speed peak onto a bright
slow body/Doppler stripe could make the actual club look like a separate ball.
The club reference now has to satisfy whole-path integrated range/Doppler consistency
and sustained braking, not just one abrupt velocity drop.

The compact original observations and separate manual return labels are regression
fixtures in `tests/fixtures/`. They contain no client address/free-text notes. The
velocity/frame bands in the annotation file are **test labels only**; production
tracking does not contain shot-specific coordinates, frame numbers or speed bands.
Ball-withheld tests are not independently recorded dry swings. Actual dry-swing
captures are still needed to establish a real-world false-positive rate.

## Detection model

The live and replay paths use the same `ShotDetector` implementation:

1. **Read the actual waveform.** Range/Doppler bin widths, frame period and the
   acquisition FOV come from the supplied `profileCfg`, `chirpCfg`/`frameCfg`, and
   range `cfarFovCfg`. The implementation supports the standard single-profile
   TDM frame configuration. It never assumes a tee at 2 m, a 7 m software gate,
   a 50 Hz sensor, or a particular measured shot speed.
2. **Estimate background motion.** A rolling median/MAD with a Doppler-quantization
   uncertainty floor separates moving returns from stationary background. It
   replaces the fixed 2 m/s software cutoff. Firmware CFAR still determines which
   points reach the app; the app adds no fixed SNR rejection threshold.
3. **Search backwards.** After collecting stroke context, a reverse-time DAG links
   outgoing returns using range integration, Doppler changes, spatial direction and
   measurement uncertainty. It retains short suffixes as well as longer paths, so
   a long club prefix cannot erase a late ball tail. Missing frames use the configured
   association horizon. The final choice is the **furthest valid outgoing path**,
   with fit/support quality as a tie-breaker, rather than simply the cleanest path.
4. **Fit flight jointly.** Weighted position and Doppler observations estimate
   position/velocity, with gravity and locally approximated quadratic air drag.
   Radial and angular measurement errors are treated separately. Angular error
   also propagates into the Doppler projection; noisy direction cosines are not
   treated as exact. The model-consistency decision uses a normalized residual
   statistic and its degrees of freedom, not a maximum XYZ error in metres.
5. **Observe the club's reach.** A separate motion graph finds coherent braking
   swing paths; the club is allowed much greater acceleration than free flight.
   Range and Doppler must agree globally, and braking must be sustained beyond a
   single discontinuity. Related braking prefixes are joined into a conservative
   observed envelope. Shared candidate/club measurements remain in that envelope:
   removing them would let the last part of one club path validate itself.
6. **Validate separation.** A path needs preceding swing observations and a
   backward launch connection. It must either extend significantly beyond the
   observed club envelope, or have several actual concurrent independent returns
   ahead of the club plus resolved relative velocity/separation growth. Interpolated
   club poses can fill short gaps but do not replace the minimum actual concurrent
   evidence. The late-tail mode can work after the club disappears.
7. **Close on evidence/quiet.** Normal quiet frames resolve a stroke. Unrelated
   moving people need not hold it open: a registered flight and its club envelope
   can close after both stop extending for the association horizon. There is no
   deadline measured from first club motion. CPU/observation budgets are explicit;
   exhausted or truncated searches remain unconfirmed and are logged.

## Configuration and assumptions

`configs/swing.json` exposes the complete set of statistical settings, sensor-array
uncertainty calibration, ball/air parameters, minimum evidence and resource limits.
It contains **no shot-specific locations or speed/timing cutoffs**. Defaults are
general statistical confidence levels and physical/sensor assumptions, not values
fitted to this recording. Unknown/obsolete fields fail validation, so an old
`max_swing_distance_m` or `club_clearance_m` file cannot silently keep those gates.

- Range and Doppler standard deviations start from bin width / sqrt(12), the
  quantization uncertainty of a uniform bin. `measurement_uncertainty_scale` is
  an explicit calibration factor for additional installation/sensor error.
- `azimuth_resolution_sine` and `elevation_resolution_sine` default to the
  IWR6843ISK virtual-array geometry (eight azimuth/four elevation elements). Array
  layout is **not encoded in a TI CFG**: change these calibration settings for a
  different board. They are uncertainty estimates, not launch-angle restrictions.
- `forward_axis` and `up_axis` describe the radar mounting; defaults are +Y/+Z.
  There is no fixed lateral lane or maximum direction/elevation angle.
- Ball diameter/mass, air density and drag coefficient are physical priors and
  are configurable. Acceleration is locally approximated over the observed short
  flight segment; this is not a full outdoor flight/spin estimator.
- All sigma levels, evidence counts, fit iterations, gap/quiet/context frames and
   hypothesis/event caps are serialized into the live session metadata. Resource
   settings trade computation against the number of competing trajectories kept.
- `context_frames` bounds launch look-back. `max_event_frames` bounds a continuous
  motion event; `max_event_observations` and `max_backward_fits` bound storage and
  fitting work. These are resource/association settings, not tee/club distances.

The app cannot reconstruct a ball the firmware did not report, remove velocity
aliasing from insufficient data, or reliably distinguish physically ambiguous
club/ball observations. Short/noisy trajectories can have substantial angle
uncertainty even when outward speed is resolved. Fit residuals, velocity standard
deviations, chosen hypotheses and the club-detachment evidence are logged for
inspection. The physical acquisition setup and real dry-swing validation matter.

## Reproduce analysis

From `radar_app/`:

```bash
cargo run --release -- replay-live \
  logs/radar-live/1793296169926267431-24640 configs/swing.json \
  logs/radar-live/1793296169926267431-24640/backward-analysis.json
```

This uses the recording's `radar.cfg`, original decoded points and arm/reset
history. Every point is re-evaluated; original filter decisions are not reused.
Original swing numbers are attached to overlapping replay attempts for comparison.
The replay preserves the original arm history rather than simulating the game
disarming after a newly accepted shot. A replay end with an unresolved attempt is
reported as aborted, never promoted to a ball merely because the file ended.

From the repository root, inspect rejected points and chosen fit uncertainties:

```bash
python3 tools/analyze_live_session.py \
  radar_app/logs/radar-live/1793282339202354539-12936 \
  --summary-only --replay-report \
  radar_app/logs/radar-live/1793282339202354539-12936/adaptive-replay.json
```

For the labelled capture windows and before/after path comparison:

```bash
python3 tools/analyze_live_session.py \
  radar_app/logs/radar-live/1793296169926267431-24640 --captures --summary-only \
  --replay-report radar_app/logs/radar-live/1793296169926267431-24640/backward-analysis.json
```

Omit `--summary-only` for a point-by-point view around each original trigger.
`--before-s`, `--after-s` and `--min-speed-mps` control this **report view** only;
they never change the detector or label observations as club/ball. `--out` saves
the original-point report as JSON. All original capture files remain intact.
